## 1. What this product is (context, do not skip)

A browser-native 3D workspace that shows Indian Ocean model fields (temperature, salinity,
currents, chlorophyll) together with real point observations (Argo floats / Gliders), across
depth and time, so a forecaster/researcher does not have to switch between separate tools.
Primary user in the pitch: INCOIS operational forecasters. Secondary: researchers/students.
Tertiary: policymakers.

Core interactions promised in the deck that the demo must show:
- Rotate/pan a 3D ocean view.
- Switch between variables (temperature / salinity / currents / chlorophyll).
- Move a depth slider and a time slider and see the visualization update.
- Adjust a color scale and layer transparency/opacity.
- See Argo/Glider float markers on the 3D view; click one to open its depth profile chart.

## 3. Signal from our user survey (n=7) — read this before you start coding

We ran a short Google Forms survey and got **7 responses** (6 students, 1 IT professional; no
confirmed responses yet from an actual oceanographer or INCOIS-type forecaster). Treat this as a
small, self-selected, directional signal — not statistically solid validation — but it's real
user input and it should shape tonight's priorities. Mention the sample size honestly if you
reference it in the pitch; don't present it as more rigorous than it is.

What it told us:

- **Most-requested feature (tied, 2 votes each out of 7):** "Comparing model data with real
  observations" and "Interactive 3D ocean view." These were already core to the pitch — this is
  a signal to *not* cut them, and to make the model-vs-observation comparison visually explicit
  rather than incidental (see Section 8 below for the concrete UI this implies).
- **Also requested once each:** depth-profile charts, temperature/salinity/current/chlorophyll
  variable visualization, and "viewing changes over time" — all already in scope; no new feature
  types were requested that aren't already planned.
- **Reported difficulties working with ocean data** (free text): "difficult to compare different
  datasets," "data is difficult to understand," "difficult to understand changes over time,"
  "need to use multiple tools/software." These line up directly with the platform's stated value
  proposition — useful to quote in the pitch, but again, n=7.
- **"How easy is it to understand ocean conditions at different depths?"** (1=hard, 5=easy):
  responses were mixed and skewed toward the harder end — 2, 2, 3, 3, 3, 5, 5. Roughly half the
  respondents find depth genuinely hard to reason about. Implication: don't just show a bare
  numeric depth slider — add a plain-language cue (e.g. "50 m — thermocline" style label) so the
  UI itself teaches the user what the number means. This is a small addition with outsized payoff
  given what the survey flagged.
- **Tools currently used for ocean/environmental data:** Python, MATLAB, GIS software, "web-based
  tools," or nothing at all — respondents are a mix of technical and non-technical; the browser,
  no-install pitch resonates with the "I don't use any tools" group specifically.
- **Would they use a browser-based platform like this?** Mixed: several "Definitely," some
  "Probably," and a few "Probably not" / "Definitely no." The skeptics were mostly respondents
  who separately said they *never* face difficulty with ocean data — i.e., people without the
  underlying problem correctly don't see the need for the solution. Not a red flag on the
  product; a reminder that INCOIS forecasters (the actual target user, per the deck) are exactly
  the group *with* the problem and weren't represented in this survey.
- **One IT professional gave the lowest usefulness score (2/5)** and answered "Not sure" on
  model+observation value and "Maybe" on adoption. Single data point, but worth noting to the
  team: a working-professional, non-oceanographer audience may need clearer framing of *why* this
  matters operationally, not just a nicer view than what they have.
- **One respondent's free-text answer:** they'd first benchmark the proposed solution against
  existing platforms before deciding what to add — a fair point for the written pitch/Q&A prep,
  not something actionable in code tonight.
- **Overall clarity of the oceanographic data presented** (in the pitch/mockup they saw), 1-5:
  mostly 3-5 (one respondent left it blank). Reasonably positive baseline, nothing alarming.

Net effect on tonight's build (see updated priorities in Sections 8-9): keep the full feature set
already scoped, but (a) make model-vs-observation comparison an explicit, visible UI moment
rather than something implicit in having both types of data on screen, and (b) add plain-language
depth labels since depth comprehension was the one place respondents self-reported real
difficulty.

## 4. Architecture

```
┌─────────────────────────────┐        HTTP/JSON        ┌───────────────────────────────┐
│         FRONTEND            │  <───────────────────>  │           BACKEND              │
│  React + Three.js + Chart.js│                          │  FastAPI + xarray + numpy      │
│                              │                          │                                │
│  - 3D ocean scene            │                          │  - /variables                  │
│  - Control panel (inputs)    │                          │  - /field  (grid slice)        │
│  - Argo marker layer         │                          │  - /floats (list + profile)    │
│  - Depth-profile chart panel │                          │  - Data adapter layer          │
└─────────────────────────────┘                          └───────────────┬───────────────┘
                                                                            │
                                                                  ┌─────────▼─────────┐
                                                                  │  Data layer         │
                                                                  │  synthetic NetCDF   │
                                                                  │  (xarray Dataset)   │
                                                                  │  + mock Argo JSON   │
                                                                  └─────────────────────┘
```

Design principle carried over from the deck's "Feasibility" slide: the backend must expose data
through one `DataAdapter` interface, with today's implementation being `SyntheticAdapter`
(reads a locally generated `.nc` file). A future `INCOISAdapter` or `ArgoLiveAdapter` should be
able to be dropped in without changing the API contract or the frontend. Build it this way even
though only the synthetic one exists tonight — it's a genuine judged point ("modular data
adapters support future datasets").

## 5. Tech stack

**Frontend**
- React (Vite) + TypeScript
- Three.js for the 3D scene
- Chart.js (via react-chartjs-2) for the depth-profile popup chart
- Zustand or plain React state for UI state (variable, depth, time, colorscale, opacity)
- Axios or fetch for API calls

**Backend**
- Python 3.11+, FastAPI, Uvicorn
- xarray + numpy for the in-memory synthetic dataset and slicing
- netCDF4 or h5netcdf as the xarray backend engine
- CORS enabled for local dev (frontend on a different port)

**Data**
- One synthetic NetCDF file with dims `(time, depth, lat, lon)` and variables
  `temperature, salinity, u_current, v_current, chlorophyll`
- One `floats.json` with ~15-30 mock Argo floats: `{id, lat, lon, profile: [{depth, temperature, salinity}]}`

## 6. Data generation script (build this FIRST)

Create `backend/scripts/generate_synthetic_ocean.py` that produces `backend/data/ocean_demo.nc`:
- Grid: lat 0°–25°N, lon 60°–95°E (Indian Ocean / Bay of Bengal + Arabian Sea box), ~1° resolution
- Depth levels: [0, 10, 25, 50, 100, 200, 500, 1000] meters
- Time steps: 8 steps (e.g., 3-hourly across one day, or 8 days — either is fine, label clearly)
- Temperature: warm at surface (~28–30°C in tropics), decreasing with depth (thermocline curve),
  add smooth spatial variation (e.g., sum of a few sine/cosine terms) so it isn't flat
- Salinity: ~33–36 PSU, slight depth/spatial variation
- u_current/v_current: small-magnitude smoothly-varying vector field (for a simple arrow/streak
  overlay if time allows — optional, cut first if behind schedule)
- Chlorophyll: higher near coasts (edges of lon range), decaying with depth and offshore distance
- Also generate `backend/data/floats.json` with mock Argo floats scattered inside the grid box,
  each with a depth profile consistent with the temperature/salinity curves above (so clicking a
  float and seeing its profile visually matches the 3D scene — this consistency is worth the
  extra 20 minutes, it's the kind of detail a judge notices).

## 7. Backend API contract

```
GET  /api/variables
  -> ["temperature","salinity","u_current","v_current","chlorophyll"]

GET  /api/meta
  -> { depths: [0,10,...], times: ["2026-09-10T00:00:00Z", ...], lat_range: [...], lon_range: [...] }

GET  /api/field?variable=temperature&depth=50&time_index=2
  -> {
       variable: "temperature",
       depth: 50,
       time: "2026-09-10T06:00:00Z",
       lat: [...],            # 1D array
       lon: [...],            # 1D array
       values: [[...],[...]], # 2D array [lat][lon], nulls allowed for land/no-data
       min: <float>, max: <float>   # for auto colorscale bounds
     }

GET  /api/floats
  -> [ { id, lat, lon } , ... ]   # lightweight list for placing markers

GET  /api/floats/{id}
  -> {
       id, lat, lon,
       profile: [ {depth, temperature, salinity}, ... ],          # observed
       model_profile: [ {depth, temperature, salinity}, ... ]     # model value at this lat/lon,
                                                                    # nearest time step — added
                                                                    # for the "compare" feature
     }
```

`model_profile` is generated the same way as `/api/field` values, just sampled at the float's
exact lat/lon for every depth level instead of returning a full grid — `SyntheticAdapter` should
do this with `.sel(lat=..., lon=..., method="nearest")` on the same dataset used for the field
endpoint, so the two are guaranteed to be consistent with each other.

Implement `DataAdapter` as an abstract base class with `get_variables()`, `get_meta()`,
`get_field(variable, depth, time_index)`, `list_floats()`, `get_float(id)`. `SyntheticAdapter`
implements it by opening `ocean_demo.nc` with xarray and `.sel()`/`.isel()` slicing, and reading
`floats.json`. Wire it up behind a single dependency-injected instance so swapping adapters later
is a one-line change.

## 8. Frontend: screens, input fields and data fields (be generous with these — the deck's tone
   and the SIH judging rubric both reward visible interactivity, not just a passive render)

**Layout:** left control panel, center 3D viewport, right-side collapsible panel for the
depth-profile chart (opens on float click), top bar with title/legend.

**Input fields / controls (left panel):**
- Variable selector — dropdown or icon toggle group: Temperature / Salinity / Currents / Chlorophyll
- Depth slider — discrete steps matching the dataset's depth levels, shows current value in
  meters **and a plain-language band label next to it** (e.g. "0 m — Surface", "50 m —
  Thermocline", "500 m — Deep water"). This came directly out of the survey: roughly half of
  respondents rated understanding ocean conditions at depth as hard (2-3/5), so don't ship a bare
  number here — a one-line hardcoded lookup table from depth to band name is cheap and directly
  answers that feedback
- Time slider (or a simple play/pause + slider) — shows current timestamp, optional auto-play
- Colorscale selector — at least 2 palettes (e.g., thermal for temperature, viridis for chlorophyll)
- Opacity/transparency slider for the surface layer
- Show/hide toggle for Argo float markers
- **"Compare model vs. observation" toggle** — this is new, added because it was the single
  most-requested feature in the survey (tied at top with the 3D view itself, and both were
  already core to the pitch). When ON, and a float is selected, show the model's value at that
  float's lat/lon/depth/time *next to* the float's actual recorded value (e.g. two numbers with a
  Δ, or two overlaid lines on the depth-profile chart — see below). Don't leave this as something
  a judge has to infer from two panels being open at once; make the comparison the visible point
  of the interaction
- Optional: a simple search box to jump to a float by ID

**Data fields shown to the user (read-only, computed/fetched):**
- Legend with min/max and a gradient bar matching the active colorscale and current field's range
- Hover tooltip on the 3D surface: lat, lon, depth, variable value at cursor
- Selected float info card: float ID, lat/lon, last depth recorded
- Depth-profile chart panel (Chart.js line chart): depth on Y (inverted, 0 at top) vs
  temperature and salinity as two series, for the clicked float. **When "Compare" is ON, add the
  model's temperature/salinity profile at that same lat/lon as two more dashed series on the same
  chart**, so the model-vs-observation gap is a single glance, not a mental exercise. This is the
  cheapest way to deliver the survey's top-requested feature without a second chart widget
- Small status/footer text: dataset time range and current time step, so a judge glancing at the
  screen understands what they're looking at without narration

**3D scene behavior:**
- Render the lat/lon grid as a plane (or gently curved surface) with per-vertex or per-texel color
  from `/api/field`, colored via the active palette and the field's min/max
- Re-fetch and re-color when variable, depth, or time changes (debounce slider drags)
- Render Argo floats as small raised markers/pins above the surface at their lat/lon; raycast on
  click to identify which float was clicked and open its profile panel
- Basic OrbitControls (rotate/pan/zoom) — this alone sells "3D ocean view" on stage

## 9. Suggested build order (do this in order; each step should leave you with something that runs)

1. Data generation script → produces `.nc` + `floats.json`. Verify by printing shapes/ranges.
2. FastAPI skeleton with the 5 endpoints above, backed by `SyntheticAdapter`. Test with curl/Swagger UI (`/docs`).
3. React app skeleton with the control panel wired to local state only (no 3D yet, no backend calls yet) — get all inputs working and logged to console.
4. Wire control panel state to `/api/field` calls; render the returned grid as a flat colored plane in Three.js (no fancy shading yet — a colored `PlaneGeometry` with a `CanvasTexture` built from the values array is the fastest path).
5. Add depth/time/variable reactivity — confirm the plane recolors correctly when each control changes.
6. Add colorscale + opacity controls to the render.
7. Add Argo float markers from `/api/floats`, raycasting for click detection.
8. Add the depth-profile side panel wired to `/api/floats/{id}`, rendered with Chart.js —
   include both the observed and `model_profile` series now (don't treat this as a stretch goal;
   the survey ranks it as important as the 3D view itself).
9. Add the plain-language depth-band label next to the depth slider (cheap, directly answers the
   survey's depth-comprehension feedback — don't skip it for time).
10. Polish pass: legend, tooltip, footer status text, loading states, and one clean color theme.
11. Only if time remains: currents as arrow/streak overlay, camera fly-to on float click, play/pause time animation.
